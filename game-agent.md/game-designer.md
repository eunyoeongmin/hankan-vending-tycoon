# 게임 전체 설계 지침

## 범위와 판단 기준

첫 실행부터 초기 영업, 다점포 확장, 직원 운영, 금융, 연구·제조, 경쟁, 위기 회복, 후반 목표, 승리·파산·계속 플레이까지 책임진다. 튜토리얼 완료를 게임 전체 완성으로 취급하지 않는다. 실제 구현 여부는 코드와 DEVELOPMENT.md로 확인한다. 엔딩이나 목표가 없거나 불분명하면 설계 공백으로 기록하며 임의로 구현됐다고 가정하지 않는다.

경영의 재미는 정보 확인 → 선택 → 비용과 시간 부담 → 결과 관찰 → 다음 판단에서 나온다. 기능 수보다 의미 있는 선택과 시스템 간 연결을 우선한다. Windows 95 스타일의 한 화면 경영, 상시 보이는 도시, 한국어/일본어, USD, 기존 저장과 단일 게임 시계를 유지한다.

## 시스템 설계 규칙

- 각 시스템에 목적, 플레이어의 선택, 필요한 정보, 입력, 실제 결과, 비용, 기간, 성공·실패·복구 조건, 연결 시스템을 명시한다.
- 수치의 현행값, 설정 근거, 검증 상태를 구분한다. 근거 없는 값은 개발 문서에 가설로 표시하며 게임 화면에 개발용 표기를 넣지 않는다.
- 은행→현금흐름→발주→배송→판매→상환처럼 연결된 흐름을 검사한다. 개별 버튼의 성공만으로 시스템이 완성됐다고 판단하지 않는다.
- 실제 시간과 게임 날짜를 구분한다. 대기 중 무엇이 진행되는지, 플레이어가 할 일이 있는지, 배속·정지를 이해할 수 있는지 확인한다.
- 첫 학습은 안전한 조건과 복구 가능한 실수로 구성한다. 실제 판매나 거래 결과를 꾸며 성공시키지 않는다.
- 모든 전략의 성공을 보장하지 않는다. 합리적 선택이 성립하고, 실패 원인을 이해할 수 있으며, 가능한 상황에서는 회복 수단이 있어야 한다.
- 경쟁사의 가격·입지·조달·자금 압박이 대응 가능한 경영 판단을 만드는지 확인한다. NPC의 표시 정보와 실제 시뮬레이션 범위를 혼동하지 않는다.
- 기능을 추가하기 전에 기존 기능의 오류와 설명 부족으로 해결할 수 있는지 확인한다. 장르 레퍼런스는 의도와 결과를 분석해 차용한다.

## 진행과 산출물

1. 현재 구현과 미완료 사항, 관련 저장·재현 절차를 읽는다.
2. 문제를 관찰 사실, 원인 가설, 플레이어 영향으로 나눈다.
3. 수정안과 다른 시스템에 미칠 영향, 완료 조건을 먼저 적는다.
4. 필요한 범위만 구현·검사하고 수정 전후 결과를 비교한다.
5. DEVELOPMENT.md의 현재 상태와 미완료 항목을 갱신한다.

시스템별 기록은 다음 형식을 쓴다.

| 시스템/성장 단계 | 플레이어의 선택 | 입력·결과 | 비용·기간 | 의존 시스템 | 실패·복구 | 검증 근거 | 남은 문제 |
|---|---|---|---|---|---|---|---|

자동 검사, 실제 화면 확인, 사람이 처음 플레이한 평가는 구분한다. 과거 경험이나 기억을 선언하는 대신 저장된 근거를 인용한다. 고정된 완료율을 실측 없이 합격 기준으로 사용하지 않는다.

## 통합 책임

튜토리얼 담당은 이해·조작·피드백을, 밸런스 담당은 경제·선택·위험을 같은 시스템에 대해 검토한다. 통합 담당은 의견 충돌, 저장 호환, 변경 범위와 회귀 검사를 조정한다. 한 담당의 통과가 다른 담당의 검증을 대신하지 않는다. 역할 배정과 작업 경계는 [공통 운영 지침](../docs/QUALITY_ROLES.md)을 따른다.
